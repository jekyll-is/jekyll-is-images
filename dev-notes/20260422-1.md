# Привет. Посмотри и прокомментируй наброски к проекту.

Посмотрел наброски: это уже не просто идеи, а довольно цельная **архитектурная схема** для плагина/пайплайна изображений в Jekyll. В целом направление сильное: есть разделение на входы (`srcdir`, `assetdir`, external), единый кеш, генерация форматов, поддержка IAL/Markdown-параметров и отдельные ветки для SVG, панорам и legacy-режима.[^1_1]

## Что выглядит удачно

- **Хорошо выделен pipeline**: parse → enrich AST → generate assets → render HTML → cleanup cache. Это правильная последовательность для Jekyll-плагина, потому что она позволяет отделить разбор Markdown от файловой обработки и финального HTML.[^1_1]
- **Есть явная модель входов**: локальные исходники, ассеты и внешние URL обрабатываются по-разному. Это снижает количество неявных правил и упрощает поддержку.[^1_1]
- **Кеширование продумано**: ключ на основе содержимого файла и параметров обработки — это сильное решение для повторных сборок и CI.[^1_1]
- **Поддержка нескольких сценариев**: обычные изображения, responsive `picture/srcset`, SVG с правкой размеров, панорамы Pannellum, legacy-совместимость. Это делает проект реально полезным не только для одного узкого кейса.[^1_1]


## Что стоит уточнить

- **Где именно жить логике: AST или HTML-конвертер**. В заметках есть оба варианта, и это важный архитектурный выбор. Если обогащать AST раньше, будет проще принимать решения о генерации; если делать это на этапе конвертации, может быть проще встраиваться в существующий kramdown-пайплайн.[^1_1]
- **Фронт-маттер пока выглядит недоопределённым**. Идея хранить image-поля в `page.data` хорошая, но нужно чётко понять: это источник данных для шаблонов, отдельный реестр медиа или часть обработки изображений. Сейчас это смешано с идеями о postread/prerender/on-demand.[^1_1]
- **Спецификация IAL-параметров требует формализации**. Сейчас перечислены `format`, `quality`, `width`, `height`, `crop`, `panorama`, `gallery`, `shape`, `inline`, но не описаны приоритеты, допустимые значения и конфликтующие комбинации.[^1_1]


## Риски в текущем виде

- **Слишком много функций в одном MVP**. Если одновременно делать crop, resize, WebP/AVIF, srcset, SVG, Pannellum, front-matter и legacy IAL, можно распылиться. Лучше жёстко выделить MVP и отложить расширения.[^1_1]
- **Не хватает единой модели метаданных изображения**. Сейчас метаданные разбросаны между IAL, front-matter, конфигом и внутренним кешем. Без общего формата это быстро приведёт к путанице.[^1_1]
- **Cleanup orphaned files может быть опасным**. Если удаление делается только по кеш-мэппингу, нужно очень аккуратно учитывать инкрементальные билды и изменение путей, чтобы не удалить ещё используемые файлы.[^1_1]


## Что я бы предложил

1. Зафиксировать минимальный контракт данных:
`source`, `kind`, `variants`, `output_path`, `cache_key`, `render_mode`, `extra_attrs`.
2. Выбрать один основной слой расширения: либо AST-first, либо converter-first, и не дублировать логику в обоих местах.
3. Разделить MVP на три этапа:
    - базовые изображения + IAL + кеш;
    - `picture/srcset` + WebP/AVIF;
    - SVG/panorama/front-matter/cleanup.
4. Описать правила приоритета: что главнее — IAL, front-matter, конфиг или значения по умолчанию.
5. Для каждого типа изображения сделать отдельную таблицу сценариев: вход → обработка → HTML → кеш.[^1_1]

## По документации и экосистеме

Судя по набору репозиториев, у вас уже есть нужные кирпичики: `is-kramdown-hooked` для интеграции с kramdown и `is-ial-parser` для разбора IAL, так что логично строить этот проект поверх них, а не заново переизобретать синтаксический слой. Это выглядит как правильное направление для дальнейшей спецификации API.[^1_1]

Если коротко: **идея сильная, структура перспективная, но сейчас главная задача — сократить неопределённость в точках интеграции и зафиксировать MVP**.[^1_1]

# AST-first, но не отказываемся от конвертера полностью.

IAL >> front-matter >> config >> defaults

Да, это хорошее уточнение: **AST-first как основная архитектура, но конвертер оставить как слой рендера и совместимости**. Иерархия источников `IAL >> front-matter >> config >> defaults` тоже выглядит логично: локальная разметка должна побеждать страницу, страница — конфиг, а конфиг — дефолты.[^2_1][^2_2][^2_3]

## Что это означает на практике

AST-first хорошо сочетается с вашей целью добавлять изображения как сущности ещё на этапе разбора Markdown: kramdown-подход и хуки после парсинга как раз предназначены для такого расширения AST.[^2_4][^2_1]
Конвертер при этом не исчезает, а становится слоем, который уже по **обогащённому AST** решает, как именно отрендерить узел: `img`, `picture`, `svg`, `panorama` и т. п. Такой подход ближе к модели Jekyll plugins, где converter отвечает за итоговый HTML-вывод, а не за всю логику извлечения смысла из Markdown.[^2_5][^2_2]

## Приоритеты данных

Ваш порядок приоритетов я бы зафиксировал именно так:

1. `IAL` — самый близкий к конкретному изображению источник параметров.
2. `front-matter` — глобальные/страничные значения, полезные для списков, обложек, галерей и дефолтных правил страницы.
3. `config` — настройки проекта и профилей обработки.
4. `defaults` — безопасные значения по умолчанию для всех случаев.

Это хороший дизайн, потому что он делает поведение предсказуемым: чем локальнее контекст, тем выше приоритет.[^2_2][^2_3]

## Как бы я оформил архитектуру

- **Parser/AST hook**: находит изображения, читает IAL, связывает их с `page.data` и конфигом, строит внутреннюю модель узла.
- **Image processor**: по этой модели вычисляет variant’ы, кеш-ключи, пути и метаданные.
- **Converter**: превращает уже подготовленные узлы в HTML и может оставаться точкой интеграции с Jekyll/kramdown.
- **Cleanup stage**: удаляет неиспользуемые производные файлы по манифесту, но не участвует в логике выбора параметров.[^2_1][^2_2]


## Что важно зафиксировать в спецификации

- Кто выигрывает при конфликте `width`, `height`, `format`, `quality`, `crop`.
- Какие параметры допускаются только в `IAL`, а какие можно брать из front-matter.
- Как наследуются правила для галерей и обложек: по странице, по блоку или по конкретному изображению.
- Что делать, если IAL противоречит front-matter, например `format: original` в IAL и `formats: [webp, avif]` в странице.


## Моя оценка решения

Это направление выглядит **сильнее**, чем чисто converter-first, потому что вам нужен не просто рендер, а полноценная семантическая обработка медиа до рендера. При этом конвертер не теряется и остаётся полезным как последний слой, что особенно хорошо ложится на Jekyll-экосистему.[^2_5][^2_2]

Можно следующим сообщением я могу предложить уже конкретную таблицу: `источник параметра → какие поля хранит → где применяется → кто имеет приоритет`?

# Предложи, посмотрим.

Да — в таком виде это уже можно считать **первым правилом архитектуры**. Я бы зафиксировал его как: AST-first для семантики и обработки, конвертер — только как слой финального рендера и совместимости; приоритеты данных: `IAL > front-matter > config > defaults`.[^3_1][^3_2][^3_3]

## Что это даёт

Такой расклад хорошо отделяет смысл от представления: AST собирает и нормализует данные изображения раньше рендера, а converter уже решает, во что это превратить — `img`, `picture`, `svg`, `div` для панорамы и т. д..[^3_4][^3_1]
Это особенно полезно в Jekyll, где converters по документации отвечают за преобразование входного формата в HTML, но при этом Jekyll также поддерживает hooks и плагины, которые позволяют вмешиваться раньше или рядом с этапом конвертации.[^3_2][^3_5][^3_6]

## Как я бы формализовал приоритеты

| Источник | Роль | Пример ответственности | Приоритет |
| :-- | :-- | :-- | :-- |
| IAL | Локальная настройка конкретного изображения | `crop`, `width`, `format`, `quality`, `inline` | 1 |
| front-matter | Настройки страницы/набора изображений | `cover`, `gallery`, `image_defaults` | 2 |
| config | Настройки проекта и профилей | `formats`, `sizes`, `legacyprocessing` | 3 |
| defaults | Безопасные значения системы | `format=original`, `quality=auto` | 4 |

Jekyll front matter по документации действительно предназначен для задания переменных страницы, доступных через `page.*`, так что использовать его как второй уровень конфигурации логично.[^3_3][^3_7]

## Практическая схема

- **На этапе AST**: парсер kramdown находит image-node, читает IAL, прикрепляет к узлу нормализованные метаданные и отмечает тип рендера.
- **На этапе обработки**: processor резолвит итоговые параметры по цепочке `IAL -> front-matter -> config -> defaults`, вычисляет cache key и подготавливает варианты.
- **На этапе конвертера**: converter берёт уже готовую модель и выдаёт HTML, не пересчитывая правила выбора параметров повторно.

Так вы не дублируете логику, а converter остаётся тонким и предсказуемым слоем, что хорошо совпадает с моделью Jekyll converter plugins.[^3_6][^3_2]

## Что стоит записать в спецификацию

- Для каждого параметра указать, допускается ли он в IAL, front-matter и config.
- Для каждого конфликта определить правило победителя.
- Отдельно описать наследование для галерей и обложек: один файл, множество файлов, набор defaults.
- Зафиксировать, какие поля считаются “контентными” и влияют на cache key, а какие — только на HTML-атрибуты.


## Моя оценка

Это **хорошее и зрелое** решение: оно достаточно строгое, чтобы не расползтись, но оставляет вам пространство для расширения. Самое важное теперь — не спорить с самим принципом, а превратить его в таблицу правил и тест-кейсы.[^3_1][^3_2]

Следующим сообщением могу предложить уже готовую **матрицу параметров**: `параметр → IAL/front-matter/config/default → конфликт → итоговое поведение`.

# Давай.

Отлично, тогда я бы зафиксировал это так: **источники параметров и их приоритеты уже можно считать частью API**. Ниже даю рабочую матрицу, которую можно прямо положить в `dev-notes` или в черновик README.[^4_1][^4_2][^4_3]

## Матрица приоритетов

| Параметр/группа | IAL | front-matter | config | defaults | Итоговое правило |
| :-- | :-- | :-- | :-- | :-- | :-- |
| `src` / `path` | Да | Да, через страницы/коллекции | Да, базовые директории | Нет | Нормализовать в абсолютный/виртуальный путь, затем резолвить источник [^4_2][^4_1] |
| `alt` | Да | Да, для page-level fallback | Нет | Да | IAL побеждает, затем front-matter, затем default из имени файла или пустая строка [^4_2][^4_4] |
| `title` | Да | Да | Нет | Да | IAL > front-matter > defaults; `title` из front-matter не считается магическим, это обычная переменная страницы [^4_1][^4_5] |
| `class` | Да | Да, как набор базовых классов | Да | Да | Объединять, но IAL может добавлять/переопределять локальные классы |
| `style` | Да | Частично | Да | Нет | Обычно объединять осторожно; конфликты решать только по явно заданным правилам |
| `width` / `height` | Да | Да, как дефолт для страницы | Да | Да | IAL задаёт конкретный target, front-matter — page default, config — global default [^4_2][^4_1] |
| `format` / `formats` | Да | Да | Да | Да | IAL задаёт формат для конкретного узла, config задаёт список разрешённых/предпочтительных форматов |
| `quality` | Да | Да | Да | Да | IAL > front-matter > config > default |
| `crop` | Да | Да, если нужен page preset | Да | Нет | IAL управляет конкретной операцией, front-matter — стандарт страницы |
| `inline` | Да | Нет | Да | Да | IAL обычно главный, потому что это семантика конкретного изображения |
| `gallery` / `cover` / `panorama` | Да | Да | Да | Да | IAL для узла, front-matter для группы/страницы, config для режима по умолчанию |
| `legacyprocessing` | Нет/слабо | Нет | Да | Да | Это именно режим проекта, а не параметр изображения [^4_3][^4_6] |

## Что я бы сделал жёстко

- **IAL — только для локальных override-параметров**. Всё, что описывает конкретное изображение, должно иметь здесь наивысший приоритет.
- **Front-matter — для page presets**. То есть “как обрабатывать картинки на этой странице вообще”.
- **Config — для глобальной политики проекта**. Например, разрешённые форматы, качество по умолчанию, размерные профили.
- **Defaults — только для безопасного поведения, если ничего не задано**.[^4_2][^4_4][^4_1]


## Как это выглядит на примере

Допустим, в `config.yml` задано `formats: [webp, avif]`, в front-matter страницы — `image_defaults: { quality: 82, width: 1200 }`, а в IAL у конкретной картинки стоит `width=800 format=original`. Тогда итог будет такой:
`width = 800` из IAL, `format = original` из IAL, `quality = 82` из front-matter, а список доступных форматов берётся из config, если IAL не задаёт исключение.[^4_3][^4_2]

## Что нужно формально описать дальше

- Какие поля **мерджатся**, а какие **замещают** друг друга.
- Какие параметры влияют на cache key, а какие нет.
- Какие значения допустимы только на уровне page, а какие только на уровне image.
- Как обрабатываются конфликтующие классы и стили.
- Может ли front-matter задавать не только defaults, но и named profiles, например `hero`, `gallery`, `thumb`.


## Моя рекомендация по спецификации

Я бы ввёл понятие **policy layers**:

1. `defaults`
2. `config policy`
3. `front-matter profile`
4. `IAL override`

Тогда логика будет не просто “кто сильнее”, а “из какого слоя берётся значение и можно ли его переопределять локально”. Это обычно лучше масштабируется, чем простая плоская цепочка.[^4_2][^4_3]

Следующим сообщением могу уже предложить **конкретные имена полей** для front-matter и config, чтобы схема была консистентной: например, `image_defaults`, `image_profiles`, `image_formats`, `image_quality`, `image_legacy`.

# Что касается форматов: в конфиге нужна зависимость от входного формата, и не нужна множественность. Т.е. в конфиге может быть `{ :png => webp, :jpeg => :avif }` или `:webp` (для всех), или `{ :png => :webp, :_ => nil }` (где `:_` подразумевает все оставшиеся входные форматы, а `nil` — отсутствие преобразования).

Да, это хороший и очень полезный сдвиг. Я бы оформил форматы не как список доступных вариантов, а как **правило преобразования по входному формату**, где одна запись конфигурации выбирает один выходной формат или отсутствие преобразования.[^5_1][^5_2]

## Предлагаемая модель

Конфиг для форматов можно сделать таким:

```yaml
image_formats:
  png: webp
  jpeg: avif
  _: nil
```

Или в короткой форме для глобального правила:

```yaml
image_format: webp
```

Смысл такой: если задано одно значение, оно применяется ко всем входным форматам; если задана мапа, то она работает как таблица соответствий `input -> output`; `:_` — правило по умолчанию для всех неописанных входов; `nil` — оставить исходный формат без преобразования.[^5_3][^5_1]

## Как я бы интерпретировал правила

- `png: webp` — все PNG конвертировать в WebP.
- `jpeg: avif` — JPEG конвертировать в AVIF.
- `image_format: webp` — для всех поддерживаемых входов пытаться делать WebP.
- `_: nil` — для всех форматов, не перечисленных явно, не делать преобразование.
- `nil` как значение — это именно “оставить как есть”, а не “использовать дефолт”.[^5_4][^5_1]


## Почему это хорошо

Это убирает неоднозначность множественных выходов и делает конфиг детерминированным: у каждого входного формата есть ровно одно решение. Такая модель проще для кеша, проще для тестов и лучше подходит для AST-first пайплайна, где решение о вариантах надо принять один раз, до рендера.[^5_5][^5_6]
Кроме того, в Ruby и Jekyll конфиги естественно живут как hash-структуры с символьными ключами, а символы в качестве ключей — нормальная и привычная форма для подобных настроек.[^5_7][^5_3]

## Как это выглядит в приоритетах

Я бы разделил два уровня:

1. **Policy-level**: как проект в принципе преобразует входные форматы.
2. **Image-level override**: если конкретное изображение в IAL требует особого поведения.

Тогда `IAL` может, например, сказать `format=original` или `format=avif`, но глобальная config-модель всё равно остаётся таблицей одного исхода на один вход. Это особенно удобно, потому что Jekyll-конфиг обычно задаёт не только значения, но и поведение сборки, а фронт-маттер и IAL уже уточняют локальные исключения.[^5_2][^5_8]

## Что стоит зафиксировать в спецификации

- `image_formats` принимает либо scalar, либо hash.
- Hash-ключи нормализуются к символам.
- `:_` — fallback для всех неописанных входных форматов.
- `nil` — no-op, то есть оставить исходный формат.
- Никакой множественности выходов на один вход в config.
- Если входной формат не поддерживается движком, он либо проходит как есть, либо отбрасывается по отдельному правилу, но не генерирует несколько вариантов.[^5_7][^5_1]


## Мой совет по формулировке

Я бы записал это так:

> `image_formats` defines a one-to-one conversion policy from input format to output format. A scalar value applies to all inputs; a mapping applies per input format; `:_` is the fallback for unspecified formats; `nil` means no conversion.

Для вашего документа это очень удачная формулировка: короткая, строгая и легко тестируемая.[^5_1][^5_2]

# Предложи.

Ниже предлагаю рабочую форму `config.yml` для вашего image-пайплайна: она сохраняет AST-first подход, оставляет конвертер как слой рендера и поддерживает вашу схему приоритетов и одно-значную политику форматов.[^6_1][^6_2][^6_3]

## Черновик конфига

```yaml
# _config.yml

jjekyll_is_images:
  srcdir: assets
  cachedir: .jekyll-is-cache
  outputdir: assets/generated

  defaults:
    alt: ""
    title: ""
    quality: 85
    format: original
    widths: [800, 1200]
    lazy: true

  image_formats:
    png: webp
    jpeg: avif
    jpg: avif
    webp: nil
    _: nil

  svg:
    adjust_dimensions: true
    preserve_aspect_ratio: xMidYMid meet

  panorama:
    enabled: true
    tile_size: 512
    max_level: auto

  legacyprocessing: false

  profiles:
    hero:
      widths: [1200, 1600]
      quality: 80
      lazy: false
    thumb:
      widths: [320, 640]
      quality: 75
      lazy: true

  cleanup:
    enabled: true
    keep_latest: 2
```


## Что здесь важно

- `image_formats` работает как таблица преобразований: один входной формат соответствует одному выходному или `nil`. Это хорошо сочетается с вашей идеей “без множественности” и с простым кешированием.[^6_4][^6_1]
- `defaults` — это безопасный слой значений по умолчанию, который можно переопределять через front-matter и IAL.
- `profiles` — удобный способ задавать named presets для страницы или блока, если вы захотите переиспользовать наборы параметров.
- `svg`, `panorama` и `cleanup` вынесены в отдельные секции, чтобы не смешивать разные домены логики.[^6_2][^6_3]


## Как это будет читаться

Резолв параметров я бы делал так:

1. IAL.
2. front-matter.
3. `profiles` из config.
4. `defaults` из config.
5. hard defaults в коде.

То есть `profiles` — это не отдельный уровень приоритета, а именованный источник, который может быть подключён front-matter или IAL как ссылка на preset. Такой вариант хорошо масштабируется и не ломает ваш принцип `IAL > front-matter > config > defaults`.[^6_5][^6_6][^6_2]

## Что бы я поправил в имени секции

Сейчас у меня стоит `jjekyll_is_images`, но я бы рекомендовал более короткое и нейтральное имя, например:

```yaml
jekyll_is_images:
```

или даже

```yaml
images:
```

Если важно минимизировать риск коллизий, лучше использовать namespace-подобный вариант `jekyll_is_images` — это понятнее для пользователей и безопаснее для конфигов.[^6_1][^6_4]

## Как связать с вашим пайплайном

- **AST hook** читает IAL и поднимает локальные override-поля.
- **Processor** резолвит режим рендера и формат по `image_formats`.
- **Converter** только выводит HTML по готовой модели.
- **Cleanup** удаляет orphaned-generated files по манифесту, который привязан к cache key.[^6_7][^6_3]


## Что я бы вынес в документацию

- `image_formats` — one-to-one conversion policy.
- `defaults` — глобальные дефолты.
- `profiles` — именованные наборы параметров.
- `legacyprocessing` — режим совместимости, а не обычная опция изображения.
- `cleanup` — опциональный этап обслуживания кеша и производных файлов.[^6_4][^6_1]

Если нужно, следующим сообщением могу развернуть это в **точную YAML-спецификацию с комментариями к каждому полю**, чтобы её уже можно было переносить в README или в `dev-notes`.

# Минутку. Мы уже определились, что `assets` используются legacy-способом без обработки, а для новой функциональности исходные файлы берутся из `_src`.

Да, это важная поправка — тогда `assets` у нас действительно остаются как **legacy-слой без обработки**, а новый пайплайн работает только с `_src`. Это хорошо согласуется с тем, что Jekyll сам различает служебные каталоги, а поведение путей и включений задаётся конфигом и соглашениями проекта.[^7_1][^7_2][^7_3]

## Как я бы переоформил модель

- `_src` — **исходники для нового пайплайна**: здесь лежат изображения, которые надо анализировать, кешировать, конвертировать и рендерить.
- `assets` — **legacy-путь**: сюда можно просто прокидывать файлы как есть, без новой обработки.
- `outputdir`/generated — папка для производных файлов, которые создаёт ваш процессор.
- `cachedir` — отдельный внутренний кеш для манифеста и метаданных.[^7_4][^7_1]


## Что это меняет в конфиге

Тогда в конфиге лучше явно разделить два режима:

```yaml
jekyll_is_images:
  srcdir: _src
  legacydir: assets
  cachedir: .jekyll-is-cache
  outputdir: assets/generated

  defaults:
    alt: ""
    title: ""
    quality: 85
    format: original
    widths: [800, 1200]
    lazy: true

  image_formats:
    png: webp
    jpeg: avif
    jpg: avif
    webp: nil
    _: nil
```

Такой вариант чётко говорит: `_src` — источник для обработки, `assets` — только совместимость и прямой проход. Это особенно полезно, если у вас уже есть старые страницы или сторонние ассеты, которые не должны попадать в новый pipeline.[^7_5][^7_2]

## Как трактовать обработку

- Если изображение найдено в `_src`, включается новый AST-first pipeline.
- Если изображение лежит в `assets`, оно идёт как legacy asset без преобразований.
- Если путь внешний, можно оставить pass-through или обработать по отдельному внешнему адаптеру.
- Если нужно совместимость для старых материалов, `legacyprocessing: true` может включать особую ветку, но не смешивать её с `_src`-пайплайном.[^7_1][^7_4]


## Что я бы записал как правило

> `_src` is the canonical source tree for processed images. `assets` is a legacy, non-processed asset tree preserved for backward compatibility.

Это формулировка сразу снимает двусмысленность: новый код не должен “случайно” брать файлы из `assets`, а должен искать их в `_src`; наоборот, старый код не должен неожиданно начать проходить через новый конвертер.[^7_2][^7_1]

## Что подправить в прежней схеме

В прошлой версии я слишком сильно смешал `srcdir` и `assets`. Теперь правильнее:

- `srcdir: _src`
- `legacydir: assets`
- `outputdir: assets/generated` или, если хотите совсем развести, `outputdir: _site/assets/generated`
- `formats` и прочие правила применяются только к `_src`-файлам[^7_4][^7_1]


## Итог

Это делает архитектуру чище: **новый пайплайн обрабатывает только `_src`, а `assets` остаются транспортом для старого мира**. В такой модели проще тестировать, проще документировать и проще мигрировать существующий контент без поломок.[^7_3][^7_1]

Следующим сообщением могу пересобрать вам **полный и уже согласованный `config.yml`** с учётом этого разделения, без смешения legacy и нового пайплайна.
